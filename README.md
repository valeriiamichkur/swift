# SWIFT — прогноз заповненості станцій Citi Bike на годину вперед

**SWIFT** показує, які станції велопрокату Citi Bike у Нью-Йорку, найімовірніше, **залишаться без велосипедів** або **переповняться** (не матимуть вільних доків) протягом наступної години.

## Навіщо це

Станції велопрокату постійно розбалансовуються. Вранці велосипеди «стікаються» до ділових районів, а ввечері повертаються назад. Тому на одних станціях не можна взяти велосипед, а на інших — повернути. SWIFT поєднує історію поїздок із живими даними про станції, щоб заздалегідь показати проблемні місця. Це корисно:

- **велосипедистам** — щоб знати, чи вдасться взяти або залишити велосипед на потрібній станції;
- **операторам ребалансування** — щоб бачити, куди везти велосипеди і звідки їх забирати.

Проєкт побудований лише на **відкритих даних** Citi Bike і не потребує ключів API.

## Як працює прогноз

Модель свідомо наївна й прозора:

```
очікувана кількість велосипедів через 1 год =
    велосипедів на станції зараз  +  середній чистий потік станції за цю годину
```

1. **Історична база.** Для кожної станції, кожної години доби та кожного типу дня (будній / вихідний) рахується середній *чистий потік*: `прибуття − відправлення` за один день.
2. **Живий стан.** Поточна кількість велосипедів і доків береться з живого потоку [GBFS](https://gbfs.citibikenyc.com/gbfs/gbfs.json).
3. **Оцінка ризику.** До поточної кількості додається очікуваний потік за вікно `зараз → зараз + 1 год`. Якщо вікно перетинає межу години, потоки двох годин зважуються пропорційно. Якщо воно переходить із буднього дня у вихідний, для кожної частини береться свій тип дня. Далі станція отримує статус:

| Статус | Умова | Значення |
|---|---|---|
| `low` | очікувано велосипедів ≤ поріг | ймовірно, залишиться без велосипедів |
| `high` | очікувано вільних доків ≤ поріг | ймовірно, переповниться |
| `medium` | інакше | усе гаразд |

Поріг за замовчуванням — **2** велосипеди / доки, його можна змінювати в діапазоні 0–10. Станції, яких немає в історичних даних, отримують потік 0 і позначку «немає історії».

> Це оцінка, а не гарантія: модель не враховує погоду, події, свята чи роботу бригад ребалансування.

## Архітектура

```
                    ┌──────────────────────────┐
  data/raw_data.csv │  data/analyze_data.py    │  data/data.json
  (поїздки) ───────▶│  очищення + агрегація    │──────────────┐
                    └──────────────────────────┘              │
                                                              ▼
  Citi Bike GBFS ──▶ feed.py / Snapshot  ──▶  forecast.py  (спільна математика)
  (живий стан)       кеш 60 с + бекап CSV          │
                     fallback_feed.csv              │
                                     ┌──────────────┴──────────────┐
                                     ▼                             ▼
                          app.py (Streamlit)          swift-landing/server.py
                          дашборд + таблиці           /api/forecast + статика
                          charts.py, station_map.py            │
                                                               ▼
                                                    index.html, map.html
                                                    (Leaflet-карта, годинник)
```

Проєкт складається з трьох шарів.

### 1. Підготовка даних (офлайн)

**`data/analyze_data.py`** перетворює сирі поїздки (`data/raw_data.csv`, формат Citi Bike System Data) на компактну таблицю типового потоку **`data/data.json`**:

- читає лише 4 колонки: час початку й кінця поїздки та ID станцій відправлення і прибуття;
- переводить час у пояс `America/New_York`;
- бере лише повні дні періоду (1–13 вересня 2026) і виключає святковий Labor Day, бо в свята люди їздять як у вихідні;
- рахує відправлення та прибуття по сітці «станція × година × тип дня» і ділить їх на кількість днів відповідного типу;
- зберігає `net_flow` (з точністю до 0,01) і відкидає нульові години.

Структура `data.json`:

```json
{
  "meta":    { "first_day": "2026-09-01", "last_day": "2026-09-13",
               "days": { "weekday": 8, "weekend": 4 },
               "excluded": { "2026-09-07": "Labor Day" } },
  "weekday": { "<station_id>": { "<година>": <net_flow>, ... }, ... },
  "weekend": { ... }
}
```

Ключ станції — це ID з даних поїздок, який у GBFS-потоці називається `short_name`.

### 2. Ядро (спільне для обох інтерфейсів)

| Модуль | Роль |
|---|---|
| **`forecast.py`** | Чиста математика прогнозу: `predict_station_availability()`, правило «будній / вихідний» (`day_type`), поріг і його діапазон. Перевіряє вхідні дані: час має бути з часовим поясом, місткість — додатна, кількість велосипедів — невід'ємна. Запуск `python forecast.py` проганяє вбудовані тести. |
| **`feed.py`** | Завантажує GBFS (`station_information` + `station_status`) і об'єднує їх за `station_id`. Відкидає неробочі станції, кешує результат на 60 с і після кожного вдалого запиту зберігає знімок у `fallback_feed.csv`. Якщо API недоступне, повертає цей бекап із прапорцем `is_backup`. |

### 3. Інтерфейси

**Streamlit-дашборд** — `app.py`:

- `app.py` — точка входу. Один раз завантажує `data.json`, а потім кожні 60 с отримує свіжий знімок, рахує прогноз для кожної станції й перемальовує сторінку. Помилка на одній станції логується і не ламає сторінку.
- `charts.py` — будує дві таблиці «топ-10»: станції, які найшвидше спорожніють, і ті, що найшвидше переповняться (сортування за очікуваною заповненістю). Також готує точки для карти.
- `station_map.py` — карта станцій. Кольори з палітри Okabe-Ito, яку розрізняють люди з поширеними формами дальтонізму: червоно-помаранчевий — `low`, синій — `high`, сірий — `medium`.

На сторінці є повзунок порогу, лічильники за статусами, карта, дві таблиці ризику та повний список станцій.

**Лендинг і повноекранна карта** — `swift-landing/` (докладніше в [swift-landing/README.md](swift-landing/README.md)):

- `server.py` — локальний сервер лише на стандартній бібліотеці Python. Віддає статичні файли та `GET /api/forecast?day=weekday|weekend&time=HH:MM[&threshold=2]`. Використовує той самий `forecast.py`, `data.json` і `fallback_feed.csv`, що й Streamlit-застосунок, тому прогнози в обох інтерфейсах збігаються.
- `index.html` — лендинг: опис підходу, джерела даних і вбудована жива карта.
- `map.html` — повноекранна карта з панеллю керування прогнозом. Інтерактивний SVG-годинник (`js/clock.js`) і перемикач будні / вихідні задають годинне вікно, і карта перераховується під вибраний час.
- `js/station-map.js` — Leaflet-карта, яка отримує дані з `/api/forecast`. Починаючи з масштабу 15, точки стають пінами з очікуваною кількістю велосипедів.

│   ├── analyze_data.py    raw_data.csv → data.json

## Запуск

Потрібен Python 3.10+ (використовується синтаксис `X | None`).

```bash
python3 -m venv .venv
```

```bash
source .venv/bin/activate
```

```bash
pip install streamlit pandas requests
```

Згенерувати історичну таблицю потоку (потрібно лише після зміни `raw_data.csv`; готовий `data.json` уже є в репозиторії):

```bash
python data/analyze_data.py
```

Запустити Streamlit-дашборд:

```bash
streamlit run app.py
```

Запустити лендинг із картою (http://localhost:8000; працює без сторонніх пакетів):

```bash
python3 swift-landing/server.py --open
```

Перевірити математику прогнозу:

```bash
python forecast.py
```

## Джерела даних

- **Citi Bike System Data** — історія поїздок: час відправлення й прибуття та ID станцій.
- **Citi Bike GBFS** — живий потік: координати й місткість станцій, поточна кількість велосипедів і вільних доків.

## Обмеження

- Історія охоплює лише ~2 тижні (8 будніх і 4 вихідні дні), тому середні значення можуть бути «шумними», особливо для малолюдних станцій.
- Прогноз лінійний і не враховує межі станції: «очікувано» може бути менше 0 або більше місткості. Для відображення є окреме значення `bounded_expected`.
- Нові станції, яких немає в історії, прогнозуються без змін (потік 0).
